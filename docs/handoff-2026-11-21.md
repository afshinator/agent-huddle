## 3. The ticket room (`ticket-resolver1`)

Built on 2026-11-21: `rooms/templates/ticket-resolver1/` (template and three prompts), launched through
the shared `rooms/launch.sh --template ticket-resolver1`.
Two gates — @dev1 and @reviewer each check the ticket's claims independently and must both say it is
real and doable — then the fix, then @reviewer reviews the diff and runs the check. `max_hops: 20`
pays for the whole flow, two pushback rounds and one re-check; `turn_timeout_ms: 900000`; `dispatch_scope: lead`;
`launch_guard: refuse`. Verified by a dry run against a scratch repo (resolved config, prompt
snapshot) and one headless boot with a stub agent.

Two things it depends on that are easy to break:

- **Every agent is told the run's bar** (`buildDonePrompt`, appended to all role prompts, #78). Before
  that, only the lead knew it and the other two worked to an invented one.
- **The run leaves its record on the ticket.** The lead posts one comment at DONE — branch, commit,
  criteria, the checks a human can re-run, and a line saying an AI wrote it and nothing is merged. It
  never closes the issue and never changes a label: closing follows a merge. Without this, a finished
  fix is invisible from the tracker (#79's run did exactly that).
- **The room commits on `run/<slug>` and nothing else.** @dev1 makes one commit per change there; it
  never pushes, merges, or touches the base branch. Merging the run branch stays with a human.

The rest of what a ticket room needs, for reference:

1. **A template** `rooms/templates/ticket/` — `template.yaml` plus `prompts/{lead,dev,reviewer}.md`.
   No launcher of its own: `rooms/launch.sh --template <name>` is shared and takes
   `--repo/--slug/--branch/--run`.
2. **The ticket as the ask.** `run.yaml` carries `task:` and `definition_of_done:`; paste the ticket
   body, not a paraphrase. The brief prints as background, and the lead decides who acts.
3. **Prompts that assume code, unlike docs-audit's.** docs-audit tells its agents *not* to read
   source; the ticket template must say the opposite, and must require a red test before a fix
   (`~/.agents/skills/tdd`) plus a runnable check at the end of every hand-off.
4. **A reviewer whose approval carries evidence** — same rule the docs-audit reviewer now has:
   name the command it ran and the value it saw. A bare `go` is a defect.
5. **Room config to set deliberately:** `turn_timeout_ms: 600000` (a tool-using turn needs it),
   `max_hops: 12`, `dispatch_scope: lead` (the lead routes; a peer mention is context),
   `ack_scope: lead`, `launch_guard: refuse` (refuse to boot in a repo root it would scribble in).

## 4. Knobs, and the trap

| Key | Default | Effect |
|---|---|---|
| `dispatch_scope` | `anyone` | `lead` = only the lead dispatches; non-lead replies always report upward |
| `ack_scope` | `lead` | whose direct mention owes `Got it: …` |
| `turn_timeout_ms` | `300000` | a torn turn hands on what it wrote, then continues |
| `max_hops` | `12` | cap, then a wrap-up nudge and one concluding turn each |
| `launch_guard` | `warn` | `refuse` blocks a boot in a dirty or wrong directory |
| `pane_writable` | `true` | false gives a tail-only pane |

**The trap:** `src/room-run.ts` writes `run.resolved.yaml` from an explicit key list. A new room-level
key that is not added there silently reverts to its default in every run — that is how
`dispatch_scope: lead` was lost once (`c4a41ab`, and the test that now guards it). Any new room key
needs a line in `roomForSnapshot` **and** an entry in the round-trip test in `test/room-run.test.ts`.

## 5. Reading a run

- `_run/<run>/room.log` — what a human saw, no timestamps.
- `_run/<run>/agents/<id>/log.jsonl` — `spawned`, `turn_start`, `delta`, `tool_start`, `tool_end`,
  `settled`, `error`, `shutdown`.
- `_run/<run>/telemetry.jsonl` — `agent.turn` spans, settle latency, `dispatch` events naming what
  queued whom.
- `bun src/timings.ts _run/<run>` — per turn: total, dispatch → first event, tool time, longest gap
  with what preceded it, and the tokens and cost that turn spent (T12). The `stats` record it reads is
  a delta written just before `settled`, so a turn's spend is attributable; the per-agent total lives in
  `summary.json`. A gap after `tool_start` is a tool; after `delta` it is the model; after
  `turn_start` it is the provider. Only a gap with nothing in it ending in a timeout is a stall.
- The spend block at the end of a chain, and `_run/<run>/summary.json`.

## 7. How to work here

- `bun <file>`, never `npx tsx`; `rg` not `grep -r`; `fd` not `find`; `jq` not python.
- Test first, and make the **fixing test** red before the fix and green after; a control that removes
  the fix must go red again. Say so in the commit when a fixture changed because behaviour changed.
- **Three fixes today were green with dead wiring** (colour flag not passed, `dispatch_scope` dropped
  from the resolved config, `onDispatch` never assigned). Units passing is not proof: assert that the
  *producer* writes or passes the thing, and watch a live run before claiming it works.
- Rooms run in a worktree; never boot a room in this repo's root.
- Commit explicit paths, never `git add -A`; no co-authors.
- `AH_DEBUG=1` exactly; `AH_COLOR=0` for plain output; `HERDR_ENV=0` to run without panes.
