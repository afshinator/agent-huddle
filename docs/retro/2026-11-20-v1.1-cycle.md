# Retro — v1.1 cycle (2026-11-19 → 2026-11-20)

Session: 177 user turns, 1,583 tool calls, 134 failed results. Scope: v1.1 spec → tickets → implementation
(#35–#39), code review → triage (#40–#47), fixes (#40–#47), one manned run (run #3), then #48, #50, #51.
Everything shipped; backlog is empty at the end.

Findings are ordered by cost already paid. Each names the evidence, not an impression.

## 1. Steering rules exist and are ignored — replace them with a check (worst)

Counted from this session's own tool calls:

| Written rule (global `AGENTS.md` / repo `AGENTS.md`) | Violations |
|---|---|
| read file slices with the `read` tool, not `sed -n` | **211** `sed -n` calls in bash |
| new file → `write`, existing file → `edit`; no bulk rewrites | **125** `python3 -` heredocs, **219** heredoc writes |
| never `git add -A` (it swept unrelated files twice) | **34** `git add -A` |
| (no rule, but) `git checkout --` discards uncommitted work | **8** uses; one restored a pre-refactor file mid-task |

The rules are correct and cheap to state; they did not change behaviour. Two of the violations caused
damage that had to be repaired by hand: a `python3` replace matched a doc comment instead of the code
line (the `\0` in `test/shell.test.ts`), and `git add -A` swept `docs/stryker-evaluation.md` into #40's
commit.

**Fix: a hook, not another paragraph.** A `PreToolUse`-style extension that refuses `sed -n`, `cat >`,
and `python3 -` when the command writes a file, and refuses `git add -A`/`git add .`, each naming the tool
to use instead (`read`/`write`/`edit`, `git add <paths>`). Same shape as the existing
`_system/extensions/answer-only.ts`. This is outside this repo — it belongs in the agent environment.

Secondary: if the hook is not built, delete the rules. A rule with 211 violations is worse than no rule,
because it teaches that the steering file is advisory.

## 2. A fake that diverges from production hid the real cause of #51

`FakePiAgentClient.shutdown` marked the agent stopped but left a pending settle unresolved; the real
client rejects it when the child exits. Because of that gap the test suite could not see what a stop
mid-turn actually does, so the first fix (ordering the shutdown flags) went green locally and red on CI,
and the true second cause — a turn in flight reported as a failed hop — was only visible in a real room.

**Fix:** a parity test per seam: drive fake and real (stub-`pi`) through the same scenario and compare
observable effects, not internals. Cheap here because `test/pi-protocol.test.ts` already drives the real
client with a stub.

## 3. The test harness hides leaks

`test/coordinator.test.ts`'s `harness()` removes its temp room dir in `finally` without waiting for the
coordinator's outstanding work. A leaked write then fails in whichever test happens to be running — CI
attributed the ENOENT to a different test than the one that leaked it. Six local green runs said nothing.

**Fix:** after `fn()`, assert the coordinator has nothing in flight (the `shutdown()` contract now exists
for exactly that: `submitQueue` and `bootRun` are awaited). A harness that fails on leaked work turns a
CI-only flake into a local failure with the right name on it.

## 4. Filed issues carried assertions nobody ran (three in a row)

- **#48** was filed on visibility ("the warn is invisible"), which was the weaker half; the real defect was
  that the guard fired on a worktree — the placement `AGENTS.md` mandates.
- **#49** claimed the empty message is pushed to other agents as context. `syncContext` returns early on
  blank text; the claim was false and had to be corrected in public.
- **#50** proposed a test asserting no `[pi:` line reaches the room's **stdout**. The child's stderr never
  went to the coordinator's stdout, so that test passes before and after any change.

Root cause is one thing: an issue was written from a run's symptoms, and the assertion was never run
against the current code. `AGENTS.md` already says to verify an issue's claims — it does not say to verify
the *test you are proposing*.

**Fix (doc, one line):** when filing, state the assertion the proposed test would make, then check whether
it already passes. If it does, the issue is describing a symptom, not a defect.

## 5. Reading cost a fifth of the session

1,128 bash calls, of which 211 were `sed -n` and 36 `nl -ba` — reading files and line numbers through the
shell. That is the same finding as #1, counted a second way: the `read` tool was used 123 times against
211 shell reads.

## 6. Information access: diagnosing the SIGINT race required patching production source

To find out whether the coordinator's signal handler runs before the children's exit callbacks, I patched
`src/index.ts` and `src/real/pi-agent-client-real.ts` in a disposable worktree with `process.stderr.write`
lines, ran the room, and read the pane. That measurement was the whole point of the fix, and it needed two
instrumented runs.

**Fix:** one `--debug` (or `AH_DEBUG=1`) switch that logs boot/shutdown/exit ordering with cheap
timestamps. `PI_STDERR=1` (#50) covers child stderr; nothing covers the coordinator's own lifecycle.

## What worked, and should not be changed

- The **red-first + control** loop caught two vacuous tests of mine (#44's guard, #43's assertions) and
  three insufficient fixes (#51). Controls — break the fix, watch the test fail — were worth more than the
  tests themselves.
- **Live verification after the tests**: #51's first fix was green locally and wrong; only a room run said so.
- The **run note written before the run** (`docs/runs/2026-11-20-manned-run-3.md`) is what made run #3
  productive; its own command was wrong (`terminal_title` vs `label`) and fixing it in place was cheap.
- **CI as a second opinion**: it caught the #51 leak that six local runs missed.

## Candidates, ranked

1. Hook that refuses `sed -n` / `cat >` / `python3 -` writes / `git add -A` (environment; finding #1).
2. Parity test for the fake/real client seam (repo; finding #2).
3. Harness assertion against leaked coordinator work (repo; finding #3).
4. `AGENTS.md`: filing rule — state the assertion your test would make, and check it first (repo; finding #4).
5. `--debug` lifecycle logging for a room (repo; finding #6).
