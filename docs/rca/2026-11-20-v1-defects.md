## 2. Verdicts on the governing claims

### Claim 1 — "The spec specified the happy path of a system whose difficulty is failure modes."
**Artifact reading: not confirmed as stated. Confirmed in a narrower form.**

Against: §10 existed at the first commit (`095917f`, 12:37) with 5 bullets, including
"Agent exit mid-chain", "RPC parse error", "Timeout", "Boot", "Shutdown" — before any code.
So failure *policy* was not an afterthought.

For: after code existed, `docs/SPEC.md` was amended in 6 commits, and the §10 amendments are
exactly the findings:

| Commit | Time | §10 change | Finding |
|---|---|---|---|
| `3659606` | 15:28 (code since 14:23) | "agent exit → route failure to lead" rewritten to "halt, no reroute"; "timeout → failure routed to lead" rewritten to "chain halts with a notice" | the spec was **retro-fitted to the code's actual policy**, with no recorded reason (the brief's own decision table says this policy "arrived after code existed") |
| `1cca86c` | 17:26 | new bullet: pushContext failure is best-effort | #11 |
| `c005a5f` | 17:57 | new bullet: damaged log line skipped, damaged `state.json` absent | #12 |

Two of the original five bullets were *wrong* and were rewritten to match the implementation;
two failure modes that actually bit were absent. §10 today has 7 bullets; 4 were written or
rewritten after the code. But the pattern is not "happy path only" — it is **"policy specified,
mechanics unspecified"**: see Claim 2. The failure modes §10 named (agent exit, timeout) never
fired in testing; the ones it didn't name (#11, #12, #14, #17) all did.

### Claim 2 — "Seams specified signatures, not semantics."
**Confirmed.** Mechanical check: `rg -i "timeout|fail|reject|abort|throw|exit|error|idempot|concurren"`
over SPEC §9 returns only *type-level* occurrences — `SettledResult.aborted`,
`waitForSettled(agentId, timeoutMs)`, `on("error", …)`, `setStatus("error")`. There is not one
prose sentence in §9 stating:

- whether `spawn`/`prompt`/`pushContext`/`shutdown` can reject, and what the coordinator must do;
- whether `waitForSettled`'s `timeoutMs` rejects or returns `{aborted:true}` (a bare parameter
  name is the entire contract — and this is where #2 and #11 both sit);
- whether `shutdown` is idempotent (issue #14's real failure path);
- what a `stream`/`error` listener throwing does to the caller (#17);
- whether `Telemetry.emit` may fail, buffer, drop, or reorder (#14, still undocumented — #26).

Mapping: **#2** (abort semantics undefined), **#3** (§7.2's "or" made two different text sources
equally legal), **#11** (`pushContext` failure), **#14** (`Telemetry` write failure), **#17**
(listener failure). `codebase-design` reading: the seam is a shallow contract — seven call
signatures over an eight-method surface, with the *decisions the caller must make* left outside
the interface. A deep seam states the failure grammar once and lets both implementations and the
coordinator rely on it.

### Claim 3 — "Fakes shared the author's assumptions, so tests could not fail the way reality did."
**Confirmed for the three audit defects that needed a code change to test; refuted as the
explanation for #2; not applicable to #12/#13/#14.**

At the issue-filing baseline (`aabd2e0`), `FakePiAgentClient`'s `spawn`, `prompt`, `pushContext`,
and `shutdown` each had exactly one code path: record the call, succeed. No rejection was
reachable. Consequence: to write the tests for #11, #16, #17 the *fake itself* had to gain a
failure path (`test/coordinator.test.ts:213` stubs `spawn` to throw; `:310` makes
`pushContext` reject). That is the definition of a double that certifies optimism.

Against the claim: the fake *could* express `aborted: true` and a scripted `error` before the
audit (`test/seams.test.ts` asserted both), so #2 was a missing assertion, not a fake limitation.
And #12/#13/#14 live against the real filesystem and the real telemetry writer; no fake was
involved, so the fakes cannot be blamed.

### Claim 4 — "Acceptance criteria were capabilities, not boundary invariants."
**Confirmed, with the sharpest evidence being the single-sided invariant.**

Ticket DoDs (pre-code) are capability statements: T10 "persist `RoomState` … at chain
completion/halt and on shutdown" (→ #1: a rebuilt snapshot satisfies the words); T4 "unknown
`@handle` (log + skip, never crash)" (→ #6: "skip" says nothing about the routing result);
T3 "interfaces match §9 exactly" (→ #9/#18: a restatement cannot fail on semantics);
T2 "atomic `state.json` write: … no partial state on crash" — an invariant, but **write-side
only** (→ #12 is exactly its unstated read-side twin).

Caveat that cuts against the brief's canonical example: #11's AC *is* boundary-shaped
("`room.active_chains` returns to its pre-chain value on **every exit path**"). The DoD problem
was in the pre-code tickets, which is where it mattered; the post-audit issues were better
written than the tickets that produced them.

### Claim 5 — "Diff-based review cannot see absent code."
**Refuted as stated; confirmed in a form that is more useful.**

Refutation: the review round that produced #1–#9 was *not* diff-only. Two of the four review
subagents were instructed "Review the **entire implementation** … Read all `src/**/*.ts` and
relevant tests" (`01a1f544.subagents.json`), and it still produced absent-code findings
(#4 no mutex, #5 missing instruments, #8 missing validation). Absent code is visible to a
whole-implementation review.

Confirmed in this form: the review was anchored on the spec. Its brief was "Report
missing/partial requirements … against `docs/SPEC.md` and `docs/tickets/T1..T10`". A review that
measures code against a spec inherits every gap in the spec. #11–#17 are all *failure paths the
spec never required* — so no amount of diff reading against that spec would surface them. The
audit found them because `ponytail-audit`'s instruction is environment-shaped ("audit like the
senior developer who just got paged … correct, safe, holds under load"), not spec-shaped. Same
code, different oracle, seven new defects.

This also explains the flaw the brief hypothesised and the artifacts reject: the distinguishing
variable is **which oracle the reviewer used**, not whether the reviewer saw a diff.

### Claim 6 — "Tickets restated the spec rather than attacking it."
**Confirmed.**

T3: "interfaces match §9.1/§9.2 exactly" — verbatim restatement.
T6: the behaviour list is §6.3's table re-typed.
T8: the behaviour list is §7.1/§7.2 re-typed.
T1: the DoD is §3's "Rules" list minus the handle grammar — and the handle grammar is where #13
landed.
T2: the DoD re-types §4 including "recoverable cache", preserving the ambiguity that #1 and #12
both exploited.

The one place a ticket *added* a requirement outside the spec, T4's "unknown `@handle`
(log + skip, never crash)", was also the one place the implementation diverged from intent
(#6) — because the added requirement stated a behaviour ("skip") without stating the outcome.
Tickets transmitted the spec's ambiguity instead of resolving it. Note the counter-example:
T6's notes record a real defect found during implementation (async spans closing at return
time) — so attack did happen once, when the ticket was being *executed*, not when it was written.

### Claim 7 — "Nothing ran the system against a hostile environment before the audit."
**Confirmed, with timestamps.**

Session `01a1f544` (all times UTC; PST = UTC−8):

| Time | Event |
|---|---|
| 2026-11-20T01:12:05Z | "add the status done to the tickets" → `aabd2e0` |
| 01:12:27Z | `ponytail-audit` skill invoked |
| 01:13:22Z | first `kill -9` mention — *55 s after the audit started* |
| 01:13:47Z | first `/dev/full` + "unwritable" + `EEXIST` — *80 s after* |

Across the 6.5-hour session there is not one occurrence of an unwritable path, a full disk, a
killed child, or a truncated fixture before 01:13Z. The pre-audit suite's only `chmod` uses are
`0o755` to make test launchers executable. Real `pi` was exercised during T8 (`c4d612b`, "Fix
per-agent command rejection") — a real process, never a *failing* one. That distinction is the
whole finding: the environment was real, the conditions were not hostile.

## 3. Ranked process changes

Ordered by how many findings the change would have prevented, with the specific findings named.
Each is a gate, not an exhortation.

**1. Specify failure semantics per seam method in §9, as a required section, before tickets.**
For every method: can it reject, on what; timeout behaviour (reject vs `{aborted}`); idempotency;
ordering guarantees; what a throwing listener does to the caller.
*Would have prevented:* #2, #11, #14, #17 — and removed the §7.2 "or" that legalised #3.
Highest leverage because it is a template change to a section that recurs in every future seam.

**2. Every seam method in a fake needs a failure knob, and every knob needs a test.**
A fake that cannot reject is a fake that certifies the author's optimism.
*Would have prevented:* #11, #16, #17 (all three required editing the fake before a failing test
could exist), plus #2 by mandating coverage of the states the fake could already express.

**3. One hostile-environment test per persistence and IO boundary, written at ticket time, not
audit time.** Unwritable directory, truncated log, corrupt cache, killed child, full disk.
*Would have prevented:* #12, #14, #16, #17 — four of the eight audit defects, one gate, roughly
one hour of work.

**4. DoD bullets must name exit paths and state, not capabilities.**
"persist `RoomState`" becomes "`startedAt` and each agent's `pid`/`sessionDir` are identical
across boot, submit, halt, shutdown, and after re-reading the file"; "atomic write" gains its
read-side twin ("a partial final line is readable as N complete messages plus one skipped").
*Would have prevented:* #1, #12, #15.

**5. Treat any post-code spec edit as a defect signal; require the commit message to say which
side moved and why.** Six post-code SPEC commits, all silent on that question; `3659606`
rewrote §10 to match whatever the code already did, which is how the failure policy lost its
rationale.
*Would have prevented:* #5, #26, and would have forced the #11/#12 bullets into the spec before
the code instead of 5 hours after.

**6. Never verify a type-level claim with a dot-prefixed file.** Verified in this repo: a
`.dotprobe.ts` carrying `const x: number = "nope"` leaves `tsc --noEmit` exit 0; the same file
without the dot fails. The audited session used 10 distinct `.probe-*.ts` files, so every
type-level conclusion drawn from one of them was vacuous. Probes must carry a non-dot name and be
deleted in the same turn.
*Would have prevented:* the vacuous half of #9/#18's "no `any` remains" claim, and it is the
cheapest item on this list.

Not recommended, on the evidence: "review the diff vs review the whole repo". Both existed in
this cycle and neither was the differentiator (Claim 5). The oracle was.

## 5. Verified corrections to the issue artifacts

Useful because they show the review artifacts carry the same optimism as the code:

- **#14 "hangs shutdown"** — refuted. Verified with a 12-line repro on Bun 1.4.2: the floating
  `void shutdown()` promise produces an unhandled-rejection banner and **exit code 1**, not a
  hang. Neither behaviour is acceptable, but the acceptance criterion "SIGINT still reaches
  `process.exit(0)`" is untested (#27 gap 1), so the fix rests on an unverified mechanism.
- **#13 "a specialist `@lead` was silently shadowed"** — over-broad. `src/config.ts` checks
  duplicate handles before reserved handles, so a specialist `@lead` is rejected as
  `duplicate agent handle "@lead"` whenever the lead holds `@lead` — which every shipped room
  file does. The real exposure was `@all`/`@everyone` only.
- **#11's gauge-leak claim** — verified correct at report time, contrary to the brief's doubt.
  Pre-fix, `room.active_chains` was decremented only inside `finish()` (`aabd2e0:src/turn-loop.ts:219`),
  which a throwing `pushContext` never reached; `1cca86c` added the `try/finally`. The fix changed
  the mechanism, which is why the current file looks like the claim never held.
- **Line pointers** in #11/#12/#13 have drifted as expected; every claim re-checked above was
  verified by code shape, and all three reproduced at the revision they described.
