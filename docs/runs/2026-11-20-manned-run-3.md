## Why a worktree

Agents inherit the coordinator's cwd and write real files there (run #2's specialist wrote
`src/rate-limiter.ts`, `test/rate-limiter.test.ts`, `shrink/` into the repo). A worktree also makes item 4
happen: a worktree root is a git repository root, so `git rev-parse --show-toplevel` returns it and the
default `warn` guard fires — which is what you want to see once.

## The four checks

**1 — prose in a pane.** While or after a turn:

```bash
herdr pane list | jq -r '.result.panes[] | "\(.pane_id) \(.terminal_title)"'
herdr pane read <pane_id> --source recent-unwrapped | tail -40
```

Pass: sentences the agent wrote, one blank line between turns. Fail: lines like
`{"ts":"…","event":"delta","text":"."}` — the pane is on `log.jsonl` and #36 regressed.

**2 — a tool line.** Same read, grep for `[tool]`:

```bash
herdr pane read <pane_id> --source recent-unwrapped | grep -n "\[tool\]"
```

Pass: `[tool] bash {"command":"cat notes/hello.txt"}`, one line, arguments cut at 200 characters.
Fail: no `[tool]` line while `log.jsonl` has `tool_execution_start`-driven records — the seam wiring
regressed (#39).

**3 — typing mid-chain.** While the lead's turn is *running* (the pane is still writing), type into
dev1's pane:

```bash
herdr pane run <dev1_pane_id> "also check the footer"
```

Pass, three things: the line appears in dev1's pane as you typed it; after the chain settles, the room
transcript shows `[@dev1] @dev1 also check the footer`; dev1 runs once more and the lead ingests the
line as context. Fail: the line never becomes a message (inbox or poll broken), or writing it deadlocks
the room (the submit queue is behind the active chain, so it must *wait*, not drop).

**4 — the warn record.**

```bash
jq -c 'select(.msg? // "" | test("launch guard"))' rooms/run3/telemetry.jsonl
```

Pass: exactly one, with `dir` = the worktree root and `branch` = `run3`. Fail: none (guard never ran) or
more than one (#38's once-per-boot claim).
